## 1. Общие положения

1. Настоящее Соглашение об уровне обслуживания (далее — SLA) определяет измеримые обязательства Исполнителя: приоритеты обращений, сроки реакции и решения, порядок экстренного реагирования, эскалации и пост-мортемы.
2. SLA не определяет порядок взаимодействия Сторон (Регламент ТП) и состав услуг и работ (Перечень услуг и работ, далее — Перечень).
3. Рекомендуемые SLA в Перечне носят справочный характер; обязательными являются значения настоящего SLA.
4. **Ответственность.** Ответственность Исполнителя за нарушение SLA определяется Договором. Компенсации по разделу 14, если они предусмотрены, являются исключительной мерой ответственности за нарушение сроков SLA и не увеличивают ответственность сверх установленных Договором пределов.

## 2. Термины и определения

| Термин | Значение |
|---|---|
| Обращение | Заявка или сообщение Клиента, зарегистрированное в согласованном канале |
| Приоритет | Категория срочности обращения: P1–P4 (раздел 5) |
| Содержательный ответ | Ответ, содержащий статус обращения, план действий или запрос недостающих сведений. Автоматическое подтверждение получения содержательным ответом не является |
| Время реакции | Интервал от регистрации Обращения до первого содержательного ответа Исполнителя |
| Время решения | Интервал от регистрации Обращения до устранения бага по гарантии; для платных работ — до старта работ по смете |
| Инцидент | Событие, нарушающее работу сервиса Клиента |
| Критический инцидент | По определению Перечня (общие правила): событие, делающее сервис Клиента полностью недоступным или создающее риск потери данных |
| Экстренное реагирование | Круглосуточная реакция на P1-обращения вне рабочего времени (раздел 8) |
| Экстренный канал | Телефон или мессенджер, указанные в Регламенте ТП в качестве канала экстренной связи |
| Эскалация | Передача Обращения на вышестоящий уровень при нарушении сроков |
| Пост-мортем | Отчёт о причинах и мерах по подтверждённому P1-инциденту |
| Длящиеся работы | Работы, срок выполнения которых превышает 5 рабочих дней, либо работы, выполняемые на регулярной основе (поддержка, мониторинг, обслуживание) |
| Рабочее время | Рабочие дни с 10:00 до 19:00 по московскому времени. Рабочие дни определяются по производственному календарю Исполнителя (РФ) |
| Рабочий день | 8 рабочих часов в пределах рабочего времени |

## 3. Иерархия документов и приоритет

Документы применяются в следующей иерархии (от высшего к низшему):

| Уровень | Документ | Регулирует |
|---|---|---|
| 1 | Договор (лицензионный договор / договор оказания услуг) | Юридическая основа: лицензия, оплата, ответственность; состав приложений |
| 2 | Соглашение об уровне обслуживания (SLA) | Измеримые обязательства: время реакции, время решения, доступность, режим обслуживания |
| 3 | Регламент технической поддержки | Порядок взаимодействия: каналы, порядок обращений, границы поддержки |
| 4 | Перечень услуг и работ (Приложение № 4 к Договору) | Состав услуг и работ, применимость к лицензиям, ограничения ответственности |

1. При расхождении между документами приоритет имеет документ более высокого уровня.
2. При расхождении между SLA и Регламентом ТП приоритет имеет SLA.
3. При расхождении между Регламентом ТП и Перечнем приоритет имеет Регламент ТП.
4. Иерархия воспроизводится без изменений во всех четырёх документах; перечень приложений к Договору фиксируется в Договоре: № 1 — Спецификация ПО, № 2 — SLA, № 3 — Регламент ТП, № 4 — Перечень. `[+ номер «Порядка приёмки работ» — уточнить у юристов]`
5. Изменение иерархии допускается только одновременно во всех четырёх документах.

## 4. Режим обслуживания

1. **Базовый режим:** рабочее время. Все обращения, включая консультации и запросы работ, регистрируются в согласованном канале; сроки исчисляются по разделам 6–7.
2. **Экстренное реагирование:** действует вне базового режима для P1-обращений, поданных через экстренный канал (раздел 8). Для P2–P4 вне рабочего времени обращения фиксируются, время реакции исчисляется с начала следующего рабочего дня.
3. Экстренное реагирование доступно всем тарифам и оплачивается по разделу 8. Тарифные планы не включают его в фиксированную стоимость лицензии, за исключением объёма, зафиксированного для Enterprise в Тарифных планах/Договоре (п. 8.7).
4. **Плановые окна обслуживания:** работы Исполнителя, затрагивающие сервис Клиента, проводятся в плановые окна, согласованные не менее чем за 3 рабочих дня. Работы в плановые окна не считаются нарушением SLA. Внеплановые работы, вызванные критическими инцидентами, выполняются без предварительного уведомления с последующим информированием Клиента.

## 5. Классификация обращений и приоритеты

| Приоритет | Определение | Примеры |
|---|---|---|
| P1 | Критический инцидент: сервис полностью недоступен; риск потери данных; признаки компрометации; DDoS-атака, делающая сервис недоступным | Сайт не открывается; корзина и оплата не работают; подозрение на утечку данных |
| P2 | Серьёзное нарушение: ключевые функции работают нестабильно или частично недоступны, есть обходной путь; нарушения периодического характера | Периодически не работает оформление заказа; медленная работа критичных страниц |
| P3 | Некритичный баг: не блокирует основные операции | Неверный текст в подсказке; ошибка в фильтре |
| P4a | Консультация или вопрос в рамках поддержки, включая консультации по лимиту часов | Вопрос по работе платформы, запрос документации |
| P4b | Запрос услуги или работы по ID Перечня | Заявка на доработку, настройку, интеграцию |

1. Приоритет присваивает Исполнитель при регистрации; Клиент вправе предложить приоритет, обосновав его. Спор о приоритете разрешается по процедуре эскалации (раздел 9).
2. **Пересмотр приоритета.** Исполнитель вправе пересмотреть приоритет при уточнении обстоятельств — в обе стороны. Пересмотр сопровождается обоснованием, предоставляемым Клиенту по запросу. До разрешения спора обращение обрабатывается по более высокому из двух приоритетов.
3. Обращения, не соответствующие определению какого-либо приоритета, обрабатываются по ближайшему подходящему приоритету с обоснованием, предоставляемым Клиенту по запросу.
4. SLA применяется к каждому обращению отдельно. При одновременных P1-обращениях Исполнитель распределяет ресурсы и информирует Клиента о порядке обработки.

## 6. Метрики и способ исчисления

1. Сроки исчисляются в рабочих часах в пределах рабочего времени, если иное не указано в разделе 7. Все сроки исчисляются по московскому времени; Клиент самостоятельно учитывает разницу часовых поясов при подаче обращений.
2. Для P1 в экстренном режиме сроки исчисляются в календарных часах (раздел 8).
3. Течение сроков приостанавливается, пока Исполнитель ожидает данные от Клиента (п. 7.6.5 Регламента ТП) либо на период сбоя стороннего провайдера, влияющий на возможность выполнения обязательств (п. 12.3).
4. Техническая регистрация обращения в баг-трекере — немедленно (автоматически). Присвоение приоритета — в пределах времени реакции для P1–P2; для P3–P4 — не позднее 2 рабочих дней. Содержательный ответ — в пределах времени реакции, установленного разделом 7 для соответствующего приоритета.
5. Сроки по заявкам, выполнение которых зависит от третьих лиц (регистраторы, реестры, провайдеры, платёжные системы), исчисляются с учётом сроков третьих лиц; Исполнитель информирует Клиента о таких зависимостях при приёме Заявки.

## 7. Сроки реакции и решения

*(Типовые отраслевые ориентиры; финальные цифры — после согласования с отделами.)*

| Приоритет | Реакция: Бизнес | Реакция: Премиум | Реакция: Enterprise | Решение |
|---|---|---|---|---|
| P1 | 1 рабочий час | 1 рабочий час | 1 рабочий час; при активированном экстренном реагировании — 1 календарный час (раздел 8) | Обходной путь — 4 рабочих часа (в экстренном режиме — 4 календарных часа); устранение — 1 рабочий день (в экстренном режиме — 24 календарных часа); если устранение в срок невозможно — план восстановления (п. 7.4–7.10) |
| P2 | 4 рабочих часа | 4 рабочих часа | 2 рабочих часа | 3 рабочих дня; Enterprise — 2 рабочих дня |
| P3 | 2 рабочих дня | 1 рабочий день | 1 рабочий день | 10 / 7 / 5 рабочих дней (по тарифам) |
| P4a | 1 рабочий день | 1 рабочий день | 1 рабочий день | Содержательный ответ и есть решение |
| P4b | 3 рабочих дня | 2 рабочих дня | 1 рабочий день | Смета в срок реакции; старт работ — в срок, согласованный при приёме Заявки |

1. Условия реакции по P1 одинаковы на всех тарифах; различие обеспечивает экстренное реагирование как опция (раздел 8) и сроки по P2–P4.
2. Время решения по P1–P3 относится к багам по гарантии. Платные работы выполняются по смете отдельного договора. Разграничение бага по гарантии и платной доработки определяется «Порядком приёмки работ» `[№ приложения уточнить]`; SLA применяется к багам по гарантии.
3. Сроки выполнения доменных и иных операций, зависящих от третьих лиц, — с учётом п. 6.5.

### План восстановления (recovery plan)

4. План восстановления применяется, если устранение P1 в установленный срок невозможно по объективным причинам: сложность инцидента, зависимость от третьих лиц, необходимость восстановления данных.
5. Исполнитель предлагает Клиенту план восстановления не позднее чем за 2 рабочих часа до истечения срока решения по P1.
6. План восстановления содержит: перечень контрольных точек с конкретными сроками, ответственных лиц, критерии завершения работ, оценку остаточных рисков.
7. План восстановления согласуется с Клиентом через согласованный канал. Согласие оформляется ответом Клиента или иным подтверждением в согласованном канале.
8. Если Клиент не согласовал план в течение 4 рабочих часов с момента направления, Исполнитель информирует Клиента о продолжении работ по базовому SLA и предлагает эскалацию на уровень L3 (раздел 9). До согласования плана SLA продолжает действовать в общем порядке.
9. Если согласованный план предусматривает срок устранения свыше 5 рабочих дней, план дополнительно согласуется на уровне L3.
10. Соблюдение согласованного плана восстановления не считается нарушением SLA. Отклонение от контрольных точек плана без согласования с Клиентом считается нарушением SLA с момента отклонения, за исключением случаев, предусмотренных разделом 12.

## 8. Экстренное реагирование (24/7)

1. Экстренное реагирование — реакция Исполнителя на P1-обращения вне рабочего времени, включая выходные и праздники.
2. Основания: недоступность сервиса Клиента, риск потери данных, признаки компрометации, DDoS-атака. Иные вопросы (доработки, консультации, некритичные баги) в экстренный режим не переводятся — независимо от готовности Клиента оплатить работы.
3. **Активация.** Экстренное реагирование активируется обращением по экстренному каналу (Экстренный канал, раздел 2). Обращения через обычные каналы обрабатываются в базовом режиме, даже если содержат признаки P1.
4. **P1 через обычный канал вне рабочего времени.** Исполнитель при обработке уведомляет Клиента о возможности экстренного реагирования и запрашивает подтверждение. До подтверждения обращение обрабатывается в базовом режиме.
5. Время реакции — не более 1 календарного часа с момента регистрации обращения по экстренному каналу. Сроки решения по P1 в экстренном режиме исчисляются в календарных часах (раздел 7).
6. **Оплата.** Активация экстренного реагирования — стоимость 1 часа по базовой ставке соответствующей категории работ; последующее время — с коэффициентом `[1,5]` к базовой ставке; минимальная оплата — 2 часа; округление — до 30 минут. Работы фиксируются повременно (таймер, CRM, акт). Видеозапись фиксирует экран инженера в целях подтверждения объёма работ; записи хранятся у Исполнителя и не передаются третьим лицам, кроме как по запросу Клиента в рамках сверки акта.
7. **Enterprise.** `[2]` экстренных вызова в год включены в тариф. Сверх включённого объёма — по п. 8.6. Неиспользованные вызовы не переносятся на следующий год и не подлежат денежной компенсации.
8. Каждое экстренное реагирование сверх включённого объёма оформляется отдельной заявкой и закрывается актом.

## 9. Инциденты и эскалация

1. Инцидентами считаются обращения P1–P2.
2. Уровни эскалации:

| Уровень | Кто | Вступает, если | Действие |
|---|---|---|---|
| L1 | Персональный менеджер | Базовый уровень | Ведёт обращение |
| L2 | Технический ответственный | Превышено время реакции; до истечения срока решения по P1–P2 осталось 2 рабочих часа | Подключается к обращению, согласует план |
| L3 | Руководство Исполнителя | Превышено время решения по P1–P2; спор о приоритете; конфликтная ситуация | Принимает решение, информирует Клиента |

3. **Эскалация по инициативе Клиента.** Клиент вправе инициировать эскалацию через персонального менеджера (L1 → L2) или через управленческий контакт L3. Эскалация по инициативе Клиента не требует обоснования и не влияет на приоритет обращения.
4. Статус-апдейты: P1 — не реже одного раза в 4 рабочих часа (в экстренном режиме — не реже одного раза в 4 календарных часа); P2 — не реже одного раза в рабочий день.
5. Управленческие контакты уровня L3 передаются Клиенту при заключении Договора `[или фиксируются в приложении]`.
6. **Эскалация по P3–P4b.** Автоматические триггеры уровней L2 и L3 применяются к обращениям P1–P2. Для обращений P3–P4b эскалация инициируется Клиентом через персонального менеджера (L1 → L2) или через управленческий контакт L3 (п. 9.3). Нарушение сроков по P3–P4b фиксируется в отчётности (раздел 15).

## 10. Пост-мортемы

1. По каждому **подтверждённому** P1-инциденту Исполнитель готовит пост-мортем: что произошло, причины, меры по недопущению повторения. Обращения, не подтверждённые как P1, пост-мортему не подлежат.
2. Срок предоставления — не более 10 рабочих дней с момента устранения инцидента. Для тарифа Enterprise — не более 5 рабочих дней.
3. Пост-мортем доступен Клиенту любого тарифа, по чьему обращению зарегистрирован P1; для тарифа Enterprise по запросу дополнительно проводится разбор с участием технических специалистов `[опция]`.
4. Пост-мортем содержит описание инцидента в объёме, достаточном для понимания причин и принятых мер; не является исчерпывающим и не ограничивает права Сторон по Договору.

## 11. Обязанности Клиента

1. Клиент обязуется предоставлять доступы, информацию и тестовые данные в объёме и в сроки, необходимые для выполнения SLA.
2. Клиент назначает ответственное лицо (лиц) для взаимодействия по инцидентам P1–P2 и обеспечивает их доступность в согласованном канале.
3. Клиент соблюдает порядок подачи обращений, установленный Регламентом ТП, и правила деловой этики (раздел 5 Регламента ТП).
4. При нарушении Клиентом настоящих обязанностей сроки SLA приостанавливаются на период просрочки Клиента.

## 12. Исключения и приостановка SLA

1. SLA не применяется (сроки могут быть увеличены): внештатные ситуации, включая блокировку и выход из строя каналов связи; форс-мажор по Договору.
2. SLA не распространяется на проблемы, вызванные действиями Клиента или третьих лиц, кастомизацией, а также отказом Клиента от установки обновлений, устранявших возникшую проблему (п. 7.8.4–7.8.6 Регламента ТП). Такие ошибки не являются багами по гарантии, и SLA к ним не применяется. Несвоевременная, но состоявшаяся установка обновлений не является самостоятельным основанием для исключения SLA.
3. **Сбои третьих сторон.** Сроки SLA приостанавливаются на период сбоя стороннего провайдера (хостинг, регистратор, платёжные системы, SMS-шлюзы и др.), если сбой влияет на возможность выполнения обязательств. Исполнитель информирует Клиента о сбое и предполагаемых сроках восстановления.
4. Обращения, не соответствующие определению приоритета, обрабатываются по ближайшему подходящему приоритету (п. 5.3).
5. Приостановка ТП по кодексу этики (п. 5.5 Регламента ТП) приостанавливает течение всех сроков SLA на период приостановки.
6. **RPO/RTO.** SLA не устанавливает обязательств по точке восстановления (RPO) и времени восстановления (RTO) для резервного копирования; эти параметры при необходимости фиксируются сметой или отдельным соглашением.

## 13. Доступность сервисов Исполнителя `[включать — решают юристы; три варианта]`

**Вариант А (обязательство с исключениями).** Целевая доступность сервисов приёма обращений за календарный месяц: баг-трекер — `[99,5]`%, личный кабинет — `[99,0]`%. Не учитываются: плановые окна (п. 4.4), форс-мажор, действия третьих лиц и Клиента, обстоятельства раздела 12. Целевой показатель не является гарантией непрерывной работы.

**Вариант Б («как есть»).** Сервисы приёма обращений предоставляются в порядке и на условиях Договора; SLA не устанавливает показателей их доступности. Клиенту предоставляется статус-страница или канал уведомлений о сбоях.

**Вариант В (разведённая ответственность).** Доступность гарантируется только для экстренного канала; остальное — «как есть».

## 14. Компенсации при нарушении SLA `[включать — решают юристы; три варианта]`

**Вариант А — денежные кредиты (классика).** `[5–10]`% от стоимости периода за каждый подтверждённый эпизод нарушения, суммарно не более `[30–50]`% стоимости периода; только для Enterprise; исключения — раздел 12.

**Вариант Б — компенсация в работах.** При подтверждённом нарушении Клиенту предоставляются бесплатные часы работ по ставкам отдельного договора. Часы предоставляются на работы по разделам Перечня `[указать: рекомендуется 5–9]`, действительны в течение 6 месяцев с даты начисления, не суммируются сверх потолка `[N]` часов за эпизод / `[M]` часов за период. Часы сверх потолка не начисляются и не подлежат денежной компенсации. Не уменьшает выручку по лицензии, закрывается тем же процессом (акт, CRM).

**Вариант В — без денежных компенсаций.** SLA остаётся обязательством по срокам; ответственность Исполнителя ограничивается Договором (п. 1.4). Нарушение фиксируется в отчётности (раздел 15) и даёт Клиенту право одностороннего пересмотра тарифа при пролонгации `[опция]`.

Компенсация не предоставляется при нарушениях, вызванных обстоятельствами раздела 12.

## 15. Отчётность

1. Отчёт об исполнении SLA: ежеквартально для всех тарифов; ежемесячно для Enterprise `[опция]`.
2. Состав: количество обращений по приоритетам, доли соблюдения сроков реакции и решения, инциденты, пост-мортемы, компенсации (если применимо).

## 16. Порядок изменений и версии

1. К SLA применяется версия, действующая на дату подачи Заявки; длящиеся работы (раздел 2) выполняются по версии, действовавшей на дату приёма Заявки. Изменения не имеют обратной силы.
2. Переходный период между публикацией новой версии и вступлением её в силу — не менее 30 календарных дней.
3. Изменения фиксируются в `CHANGELOG.md`, вносятся через pull request с ревью технического ответственного и юридической функции.
