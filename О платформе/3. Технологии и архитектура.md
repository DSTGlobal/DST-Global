# 3. Технологии и архитектура

Страница для технических руководителей, архитекторов, ИТ-команд и владельцев проекта: как устроена DST Platform, какие инженерные решения в ней приняты и чем они подтверждены. Каждое архитектурное решение обосновано измеримыми показателями — производительности, операционных затрат и поддерживаемости, — полученными на проектах с реальной нагрузкой.

---

## 3.1. Технический профиль

Прозрачный стек без скрытых зависимостей.

PHP 8+, MySQL/MariaDB, MVC и чистая PHP-шаблонизация — стандартные технологии, знакомые любой команде разработки. Ни проприетарных движков, ни компонентов, требующих отдельной экспертизы.

| Параметр | Значение |
|----------|----------|
| Язык разработки | PHP |
| Рекомендуемая версия | PHP 8+ |
| Режим совместимости | PHP 7+ |
| СУБД | MySQL 8+ / MariaDB 10+ |
| Режим совместимости СУБД | MySQL 5+ / MariaDB |
| Веб-сервер | Apache (mod_rewrite) / NGINX |
| Архитектурный паттерн | MVC (Model-View-Controller) |
| Шаблонизация | Чистый PHP (файлы `.tpl.php`) |
| Кэширование | OpCache, Redis, файловый кэш, CDN |
| Автозагрузка | Собственная система + поддержка namespaces |

Платформа эксплуатируется в двух режимах, определяемых при внедрении в зависимости от инфраструктуры заказчика:

- **Актуальный стек** (PHP 8+, MySQL 8+ / MariaDB 10+) — полная производительность: ряд оптимизаций кэширования и обработки данных задействует возможности PHP 8. Рекомендуется для проектов с ожидаемым ростом нагрузки и стандартной практикой обновления инфраструктуры.
- **Режим совместимости** (PHP 7+, MySQL 5+ / MariaDB) — для организаций, инфраструктура которых ограничена регламентами или техническими условиями: государственный сектор, предприятия с собственными серверными мощностями, действующие среды с давно не обновляемым окружением. Функциональность платформы сохраняется полностью; ограничения касаются только отдельных оптимизаций производительности.

Переход с режима совместимости на актуальный стек выполняется обновлением окружения — без замены платформы и без миграции данных. Целевой режим и конфигурацию сервера специалисты DST Global определяют на этапе внедрения под ожидаемый профиль нагрузки.

## 3.2. Архитектура: четыре уровня

Архитектура DST Platform описывается четырьмя уровнями — от инфраструктуры до ролей пользователей. Каждый уровень решает свою задачу, а связи между ними определены явно. 

```
УРОВЕНЬ 1. ИНФРАСТРУКТУРА
  Домен → Сервер (хостинг/VPS) → DST Platform (ядро + фреймворк) → БД (MySQL / MariaDB)

УРОВЕНЬ 2. ЯДРО И ФРЕЙМВОРК
  Маршрутизация + контроллеры (MVC): Frontend | Backend | Модели | Шаблоны
  Двойственная архитектура (единое ядро): Социальная часть | Бизнес-часть
  Модули (компоненты): контент | пользователи | геолокация | поиск | API | уведомления | …

УРОВЕНЬ 3. ГОТОВЫЕ БИЗНЕС-РЕШЕНИЯ
  Интернет-магазин | Маркетплейс | Мультивендор | Мед Центр | LMS | Веб-портал |
  Доска объявлений | CRM | Социальная сеть | Мессенджер 

УРОВЕНЬ 4. ПОЛЬЗОВАТЕЛИ
  Администратор | Покупатель | Продавец | Модератор | Преподаватель | Партнёр
```

### Уровень 1. Инфраструктура

Физическая и программная среда функционирования: доменное имя, серверное оборудование и ядро платформы над СУБД. DST Platform спроектирована для эффективного использования ресурсов: типовая конфигурация — один сервер с 8 vCPU и 32 ГБ RAM — стабильно обрабатывает до 400 000 посещений в сутки при пиковой нагрузке 120–150 RPS.\* Это достигнуто за счёт минималистичной архитектуры ядра и отсутствия избыточных прослоек, характерных для фреймворков общего назначения.

База данных хранит все сущности системы. Денормализованная структура таблиц и предрасчёт агрегатов (количество отзывов, средний рейтинг) сокращают число JOIN-операций: время ответа страниц каталога в условиях реальной нагрузки — 50–200 мс.\*

### Уровень 2. Ядро и фреймворк

- **Маршрутизация и контроллеры (MVC)** — frontend-контроллеры обрабатывают публичные запросы, backend-контроллеры обеспечивают административный интерфейс; модели инкапсулируют работу с данными; шаблоны отвечают за представление.
- **Двойственная архитектура** — единое ядро объединяет социальный домен (группы, лента, стена, комментарии, форум, сообщения) и бизнес-домен (магазин, маркетплейс, заказы, доставка, платежи, CRM, тендеры, LMS). Обе части используют общие подсистемы: пользователей, прав доступа и событий. Гибридные экосистемы — например, маркетплейс с обсуждениями товаров и рейтингами продавцов — строятся без стыковки разных систем через API, что снижает латентность и упрощает отладку.
- **Модульная структура** — каждый компонент владеет своими таблицами и обращается к данным других через события, а не прямые вызовы. Новый функционал (например, модуль платежей) подключается без изменения кода существующих компонентов (например, модуля заказов). При возникновении измеримой необходимости любой модуль выделяется в отдельный сервис с минимальными изменениями — границы и интерфейсы уже определены.

### Уровень 3. Готовые бизнес-решения

Над ядром и модулями надстраивается портфель из десяти коробочных продуктов — специализированных конфигураций модулей с предустановленными настройками, шаблонами и бизнес-процессами. Каждое решение использует общие базовые модули (пользователи, права, геолокация, поиск, уведомления) и наследует возможности платформы: SEO-управление, многоуровневое кэширование, права доступа, работу с высокими нагрузками. Развёртывание — от нескольких дней.

### Уровень 4. Пользователи

Роли взаимодействуют с системой после развёртывания и различаются наборами прав доступа и сценариями использования: **администратор** (управление платформой через backend), **покупатель** (каталог, заказы, личный кабинет), **продавец** (витрина, товары, заказы через кабинет `partner`), **модератор** (проверка контента), **преподаватель** (курсы и тесты в LMS), **партнёр** (внешние интеграции через API). Все роли используют единую систему аутентификации и авторизации.

> *Показатели из внутренних нагрузочных испытаний DST Global (каталог 5 млн позиций, 8 vCPU / 32 ГБ RAM). Детали и методика — в разделе 3.10.

## 3.3. Жизненный цикл запроса

Предсказуемый путь запроса и слабая связанность компонентов.

Каждый HTTP-запрос проходит явную последовательность шагов — от роутера до шаблона, один запрос соответствует одному контексту выполнения. Компоненты взаимодействуют через систему событий: расширение функциональности не требует правки ядра.

Каждое обращение пользователя проходит предсказуемую последовательность шагов:

1. Запускается точка входа — файл `index.php`.
2. Роутер анализирует URL и определяет запрошенные компонент и действие (action); ЧПУ-адреса реализуются правилами перенаправления без потери производительности.
3. Вызывается соответствующий контроллер — frontend или backend.
4. Контроллер получает параметры запроса (URL, POST-данные и другие).
5. При необходимости обращается к модели для получения или сохранения данных.
6. Обрабатывает данные и подготавливает их к выводу.
7. Передаёт данные в шаблон.
8. Шаблон генерирует HTML и возвращает его пользователю.

Бизнес-логика сосредоточена в контроллерах — это упрощает отладку и поддержку: один HTTP-запрос соответствует одному контексту выполнения, а не цепочке сервисов.

## 3.4. Ядро системы

**Что это даёт бизнесу:** единая, предсказуемая основа, на которой работают все компоненты и коробочные решения. Ядро не нужно переписывать под каждый проект — оно обеспечивает одинаковое поведение системы независимо от конфигурации.

Ядро DST Platform — это набор базовых подсистем, которые решают низкоуровневые задачи и задают единые правила для всей системы: работа с контентом и пользователями, разграничение прав доступа, обработка запросов и маршрутизация, кэширование, шаблонизация, формы и валидация данных, работа с файлами, отправка почты, конфигурация и отладка.

Ключевое свойство ядра — **единый интерфейс**. Все компоненты и коробочные решения наследуют одни и те же базовые механизмы, поэтому ведут себя согласованно: одинаково работают права доступа, кэш, события, обработка ошибок и защита от типовых уязвимостей. Для заказчика это означает предсказуемость: функциональность, добавленная в одном решении, не ломает другое, а обновления платформы не требуют переписывания проекта.

Ядро остаётся неизменным при кастомизации — расширение выполняется через компоненты, события и наследование, без правки исходного кода. Это снижает риски при обновлениях и сохраняет совместимость с будущими версиями платформы.

| Подсистема ядра | За что отвечает |
|---|---|
| Контент и пользователи | Базовые сущности, роли, права доступа |
| Обработка запросов | Маршрутизация, контроллеры, фильтрация входных данных |
| Работа с данными | Модели, Query Builder, защита от SQL-инъекций |
| События и расширения | Хуки, подписки, слабая связанность компонентов |
| Кэширование | Файловый кэш, Redis, управление временем жизни |
| Шаблонизация и ресурсы | Шаблоны, подключение CSS/JS, мета-данные |
| Формы и валидация | Построение форм, проверка данных |
| Инфраструктура | Конфигурация, отладка, логирование, почта, загрузка файлов |

> **Метрика.** Одно ядро — 10 коробочных решений и сотни реализованных проектов на платформе. Ядро не переписывается при кастомизации, а переход между режимами эксплуатации (актуальный стек / режим совместимости) выполняется обновлением окружения — без замены платформы и миграции данных.

## 3.5. Компоненты и модули

**Что это даёт бизнесу:** функциональность собирается из независимых блоков — можно подключить нужное, не трогая остальное, и наращивать систему поэтапно.

Компоненты — это самостоятельные функциональные блоки, из которых строится проект. Каждый компонент инкапсулирует свою логику: интерфейс для пользователя, административную часть, работу с данными, шаблоны и обработку событий. Компонентом может быть каталог товаров, корзина, личный кабинет, модуль платежей, форум, система уведомлений — любая законченная функция.

Компоненты бывают разного масштаба: полноценные (с публичной и административной частью), служебные (только логика и API, без интерфейса) и обработчики событий (реагируют на действия других компонентов). Такое разделение позволяет подключать ровно тот объём функциональности, который нужен проекту, — без лишних сущностей и без необходимости дорабатывать ядро.

Компоненты взаимодействуют через события, а не через прямые вызовы. Это значит, что новый модуль подключается к системе, не изменяя код существующих: например, модуль аналитики можно добавить к работающему магазину, не затрагивая логику заказов. Такая слабая связанность упрощает поддержку, снижает риск регрессий и позволяет заменять или выделять отдельные модули в самостоятельные сервисы по мере роста проекта.

**Модули (виджеты)** — независимые блоки контента, которые размещаются в зонах страницы (шапка, боковая панель, подвал). Они позволяют управлять наполнением страниц без разработки: менять состав блоков, их порядок и содержимое через административную панель.

> **Мини-кейс.** Площадка расширяется поэтапно: от интернет-магазина до мультивендорного маркетплейса, от портала до CRM — без миграции данных и переписывания архитектуры. Новый модуль подключается к событиям, не изменяя код существующих компонентов.

## 3.6. Шаблоны и наследование

**Что это даёт бизнесу:** дизайн и оформление можно менять и кастомизировать, не затрагивая логику и не рискуя сломать систему при обновлениях.

Шаблоны в DST Platform отвечают за представление — HTML-разметку и визуальное оформление страниц. Они отделены от бизнес-логики: контроллеры и модели готовят данные, шаблоны их отображают. Такое разделение позволяет менять дизайн, не затрагивая функциональность, и наоборот — дорабатывать логику, не переписывая вёрстку.

Ключевой механизм — **наследование тем**. Дочерняя тема оформления переопределяет только те файлы, которые действительно нужно изменить (шаблоны, стили, скрипты), а остальные наследует от базовой. Это даёт два практических следствия: во-первых, кастомизация не копирует всю тему целиком и не разрастается; во-вторых, обновления базовой темы не затрагивают внесённые изменения — заказчик получает новые версии, не теряя своей кастомизации.

Управление ресурсами (стилями, скриптами, мета-данными) также централизовано: подключение CSS и JS, объединение и минификация, управление заголовками страниц, мета-тегами, Open Graph и canonical — всё настраивается из контроллеров и административной панели. Для заказчика это означает предсказуемое SEO-поведение и аккуратную загрузку ресурсов без ручной сборки.

> **Мини-кейс.** Обновление базовой темы не затрагивает кастомизацию: дочерняя тема переопределяет только нужные файлы. Смена оформления и миграция выполняются с сохранением SEO-показателей — мета-данные и карты редиректов настраиваются из интерфейса.

## 3.7. Система событий (хуки)

**Что это даёт бизнесу:** функциональность расширяется без изменения существующего кода — новые модули подключаются к работе системы, не нарушая её целостности.

Система событий (хуков) — механизм, который позволяет компонентам реагировать на действия других компонентов, не обращаясь к ним напрямую. Когда в системе происходит значимое действие — создан заказ, опубликован товар, изменён статус, обновлён профиль пользователя, — компонент, инициировавший действие, сообщает об этом через событие. Другие компоненты могут подписаться на это событие и выполнить свою логику: отправить уведомление, обновить индекс поиска, записать данные в аналитику, запустить автоматизацию.

Такая модель даёт три практических результата:

- **Слабая связанность.** Компоненты не знают друг о друге и не зависят от внутренней реализации. Новый модуль подключается к событию, не изменяя код инициатора, — это снижает риск регрессий и упрощает поддержку.
- **Расширение без правки ядра.** Вся кастомная логика выносится в обработчики событий, а ядро и существующие компоненты остаются неизменными. Обновления платформы не конфликтуют с доработками заказчика.
- **Готовность к росту.** Если модуль нужно выделить в отдельный сервис, подписка на событие заменяется на вызов по сети — без переписывания логики. Архитектура изначально готова к эволюции.

Для заказчика это означает, что система развивается поэтапно: новые функции добавляются по мере необходимости, не требуя пересборки существующей логики. А бизнес-правила — например, автоматические действия при изменении заказа — настраиваются и расширяются без участия разработчиков в рутинных сценариях.

> **Мини-кейс.** При создании заказа система автоматически уведомляет покупателя и продавца, обновляет статус, запускает документооборот и фиксирует событие в аналитике — без правки кода заказов и без изменений в ядре.

## 3.8. Работа с данными: контролируемый SQL вместо тяжёлого ORM

**Что это даёт бизнесу:** предсказуемая скорость на больших каталогах и полный контроль над нагрузкой на базу данных — без «магии» ORM, которая непредсказуемо ведёт себя при росте проекта.

Классический ORM удобен на старте, но при росте каталога и нагрузки начинает генерировать неоптимальные запросы: вместо одного прохода с JOIN и GROUP BY получается несколько отдельных запросов. На миллионах товаров разница в скорости и потреблении памяти становится критической. DST Platform сознательно отказывается от этого подхода.

Вместо ORM используется **трёхуровневая стратегия доступа к данным**:

- **Query Builder** — для типовых операций создания, чтения, обновления и удаления: удобство и автоматическая защита от SQL-инъекций.
- **Прямой SQL** — для сложных выборок, JOIN, подзапросов и агрегаций: полный контроль над планом выполнения запросов и максимальная производительность.
- **Денормализация и кэширование** — для критических по нагрузке участков: предрасчёт агрегатов (количество отзывов, средний рейтинг) и хранение в Redis и CDN.

Модель данных обеспечивает автоматическую фильтрацию и валидацию входящих данных, защиту от SQL-инъекций через подготовленные выражения и события жизненного цикла (beforeSave, afterSave).

> **Метрика.** На каталоге из 5 млн товаров страница списка товаров в DST Platform выполняется за 3–8 запросов к базе данных и генерируется за 80–150 мс при потреблении 15–25 МБ памяти — против 30–120 запросов и 1 800–4 000 мс у типовых ORM-стеков (Magento 2, WooCommerce).\*

## 3.9. Производительность и кэширование

**Что это даёт бизнесу:** производительность предсказуема при пиковых нагрузках — сайт остаётся быстрым даже при сезонных всплесках и больших объёмах контента.

DST Platform использует **пять уровней кэширования**, каждый из которых решает свою задачу:

| Уровень | Что кэшируется | Время жизни |
|---------|----------------|-------------|
| 1. OpCache | Скомпилированный байткод PHP | В памяти до перезапуска PHP-FPM / сброса кэша |
| 2. Application Cache | Результаты внутри одного запроса | Один запрос |
| 3. Redis | Списки товаров — 10 мин; карточки — 1 час; статические данные — 24 часа | По типу данных |
| 4. Page Cache | HTML-фрагменты — 30 мин; целые страницы — 5 мин | По типу контента |
| 5. CDN | Статика и HTML на периферийных узлах | До 24 часов |

Эффект от многоуровневого кэширования: до 92–95 % запросов обслуживаются из кэша, база данных получает лишь 5–8 % трафика, а латентность кэшированных запросов — менее 10 мс.\*

> **Метрика.** Cache hit rate 92–95 %: база данных обрабатывает лишь 5–8 % общего трафика, кэшированные ответы отдаются менее чем за 10 мс.

## 3.12. Архитектурные принципы

**Что это даёт бизнесу:** система развивается поэтапно и без «технологического долга» — каждое усложнение обосновано измеримой необходимостью, а не трендами.

**1. Модульный монолит как стартовая точка.** Единое развёртывание, жёсткие границы модулей, слабая связанность через события. Внутренние вызовы выполняются на уровне методов — наносекунды вместо сетевых миллисекунд; транзакции поддерживаются средствами СУБД (ACID), что критично для коммерческих операций. Экономическое следствие: 400 000 посещений в сутки обрабатываются одним сервером ($200–300 в месяц), тогда как микросервисный аналог требует кластера оркестрации ($1 200–1 500 в месяц).\*

**2. Контролируемый SQL вместо тяжёлого ORM.** Предсказуемый план выполнения запросов, оконные функции и денормализация доступны напрямую — без «магии» ORM и непредсказуемого поведения при росте нагрузки.

**3. Минималистичный фреймворк без избыточных прослоек.** Накладные расходы на пустой запрос — 3–8 мс против 25–35 мс у универсальных фреймворков; базовое потребление памяти — 5–8 МБ против 15–25 МБ. Один сервер обрабатывает в 2–3 раза больше запросов при той же вычислительной мощности.\*

**4. Принцип отложенной сложности.** Архитектура эволюционирует поэтапно: MVP с минимальными абстракциями → архитектурная дисциплина (границы модулей, событийная интеграция, инкапсуляция данных) → избирательное усложнение только при измеримых триггерах. Это исключает преждевременные усложнения (по оценке DST Global — около 90 % случаев), но сохраняет готовность к эволюции: границы модулей и события определены с первого дня.

**5. Многоуровневое кэширование как основа производительности.** Пять уровней кэша (раздел 3.9) снижают нагрузку на базу данных до долей процента трафика и делают производительность предсказуемой при пиковых нагрузках.

> **Мини-кейс.** Проект с нагрузкой 400 000 посещений в сутки обходится в $200–300 в месяц за инфраструктуру приложения — против $1 200–1 500 у микросервисного аналога. Полная инфраструктура кейса (с БД-мастером, репликами, Redis и CDN) — около $650 в месяц (раздел 3.10). Усложнение архитектуры вводится только при измеримой необходимости: рост нагрузки, нормативные требования, организационное разделение команд.

| Триггер | Метрика | Порог | Действие |
